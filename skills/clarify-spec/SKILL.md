# clarify-spec：人际表达的消歧规范

本 Skill 解决一个问题：人向 Agent 下达的文本产生二义性，而 Agent 的执行没有可靠的回溯信道可以追问。涉及两类文本。**人类表达**：需求、意图、验收标准。**过程文件**：PLAN、交接单、ADR、记忆、状态报告。Agent 之间的指令与运行时消息不属于本 Skill，由 clarify-runtime 承担。

参考 ASD-STE100 的核心论点：一份维修手册的读者无法打电话问作者「你指的是 X 还是 Y」，所以航空业用受控语言消灭了二义性。Agent 解析人的指令时处境完全相同。本 Skill 把同一套纪律推广到两类文本，覆盖中文与英文。

## 两个规范对象

**A. 人类表达**（human expression）：需求陈述、意图描述、验收标准、任务说明。
核心失效模式：强度漂移（「必须」「应当」「最好」混用）。其次是验收无量化、一句多义、模糊量词与营销词。

**B. 过程文件**（agent artifacts）：PLAN、HANDOFF、ADR、记忆文件、STATUS、CHANGELOG。
核心失效模式：缺文件头契约。其次是交接三段不全、决策无理由无备选、状态自由发挥、事实冲突无仲裁。

两类对象适用同一套表达规则；B 类额外适用过程规则。规则全文：
- `references/human-expression-rules.md` — A 类全部规则条目（H-A1…H-A14, R-A1）。
- `references/agent-artifacts-rules.md` — B 类全部规则条目（H-B1…H-B18）。
- `references/standards-map.md` — 每条规则与中英文经典标准的映射。
- `references/templates.md` — 四份过程文件的最小模板。

## 使用时机（两个姿态）

**姿态一·预检**（pre-flight）：人下达指令后、Agent 开始执行前，对指令文本做机械扫描与语义通读。发现违规时输出违规清单与优化建议，由人决定是否修订。**不静默改写他人的指令**——指令是提问者的事实，静默改写即篡改。输入已合规时直接说明，不强制制造改动。

**姿态二·改写/审查**：人明确要求「改写」「规范」「审查这份文件」时，按下方流程输出改写结果或规则对照表。改写权始终在人，预检姿态的结论可作为改写姿态的输入。

用户未指定姿态时按请求措辞推断（「检查/看看有没有问题」→ 预检；「改写/规范化」→ 改写），并在一行内声明推断结果。

## 双模式

改写前选模式；用户未指定时按文本类型推断，并在一行内声明推断结果。

**Strict（严格）**：需求条目、验收标准、任务指令、交接单、ADR。误读有实际代价的场景。执行全部规则，含硬性句长上限与关键词纪律。

**Flavored（宽松）**：README、解释性散文、评审意见。执行全部结构规则（句长、一述一义、营销词禁令），关键词纪律与量化验收按建议执行——散文需要弹性，严格改写会把澄清变成人格移植。

## 扫描清单

预检与改写前逐项机械扫描，每条都能指着具体的词或标点说出违规位置：

1. **同义轮换**：同一概念多个名称（user/customer/client；用户/客户/使用者）。修复：固定其一。
2. **关键词漂移**：「必须」写成「务必」「一定要」；MUST 与「必须」中英混用。修复：RFC 2119 关键词原词原义。
3. **模糊量词**：`等等`、`各种`、`相关`、`若干`、`之类`。修复：枚举全部项或给出确切范围。
4. **营销词**：`无缝`、`极致`、`强大`；`seamless`、`robust`、`cutting-edge`。修复：删除，或替换为挣得该词的度量值。
5. **一句多义**：复合句承载多条指令或多个条件。修复：一述一义，拆为多单句。
6. **无量化验收**：「快」「准确」「稳定」无数字。修复：给出数字、单位、阈值。
7. **悬空指代**：其/该/此/上述/前者/后者链过长。修复：就近还原名词。
8. **情态升变**：「可能失败」被改写成「失败」。这是红线——情态承载置信度，置信度是内容。

## 流程

1. **分类**。判定输入属于 A 类、B 类或混合；B 类进一步判定文件类型。混合输入分段处理。
2. **选姿态与模式**。预检或改写；Strict 或 Flavored。推断时一行声明。
3. **机械扫描**。先跑确定性 linter 得到硬性违规清单：`scripts/spec-lint.py`（B 类加 `--kind` 检查文件头契约）。
4. **改写**（仅改写姿态）。逐条修复违规，同时满足以下红线：
   - 保留原文全部事实、条件、范围限定与量化指标。更短的措辞若损失必要精度，保留较长措辞并在输出中标注。
   - 保留每个情态表达的强度；禁止把 hedges 升级为事实，禁止添加原文没有陈述的原因、频率或机制。
   - 不改动文件头契约字段名与三段式字段名（linter 按字段名匹配）。
5. **专项补齐**（仅改写姿态）。B 类补齐文件头字段；交接单补齐三段式，空段写「（无）」；ADR 补齐四要素。
6. **输出**。见输出契约。

第 3 步中需要语义判断的违规（H-A1、H-A4 等）由你在通读中标记，linter 只负责机械规则。

## 输出契约

**预检姿态**：输出违规清单与优化建议，每条指出具体违规位置：

```markdown
| 违反规则 | 原文 | 建议 |
|---|---|---|
| H-A7 模糊量词 | 支持各种主流格式。 | 枚举格式：CSV 与 JSON Lines。 |
| H-A9 无量化验收 | 响应要快。 | 给出阈值：P95 延迟 ≤ 200 ms。 |
```

清单后加一行总体建议。输入已合规时直接说明，不输出空表。

**改写姿态：只输出改写后的文本。** 不加前言、不宣布模式、不附违规计数、不做变更总结。调用方需要能直接把结果粘贴进需求文档或过程文件。唯一的允许附加项：因保精度而有意保留的较长措辞，输出末尾加一行 `保留原表述：<短语> — <损失的精度>`。无此类项时省略该行。

**应请求输出规则表**。用户要求「show the diff」「改了哪些」「哪些规则」时，输出对照表代替改写结果：

```markdown
| 违反规则 | 原文 | 改写后 |
|---|---|---|
| H-A7 模糊量词 | 支持各种主流格式与相关协议。 | 支持 UTF-8 编码的 CSV 与 JSON Lines 两种输入格式。 |
```

表后加一行说明有意未简化的内容及其原因。

## 边界

**会做**：
- 将模糊、密集、二义的中英文表达改写为短句、单一含义、主动语态、指称一致的形式。
- 预检人类指令，输出违规清单与优化建议。
- 改写姿态默认只返回结果本身；应请求时点名所用规则。
- 保留原文全部事实、条件、范围限定、量化指标与情态强度。
- 为必须保留的领域术语建议一行术语表条目。

**不做**：
- 不静默改写他人的指令。预检姿态只报告与建议，改写权在提问者。
- 不处理 Agent 之间的指令与运行时消息（A2A 消息体、工具调用、错误事件）——属于 clarify-runtime。
- 不使空洞的内容变得有内容。规范修复文本的*形式*，不修复*实质*。一段没有信息量的需求改写后只是一段干净、简短、标点正确的无信息量需求——此时直接指出内容空洞，而不是抛光。
- 不改写创意、营销、说服性文本——这些文本的要点正是语气与含混。
- 不假装达成 ASD-STE100 认证级合规。本 Skill 应用其结构与原理，未复现其受版权保护的约 900 词词典。
- 不把 linter 的零违规当作合格证明。linter 是下限检查，语义规则仍需模型执行。
- 不为简洁而损失精度。压缩不是目标，消歧才是；当句子已无非确定解读时停止。
