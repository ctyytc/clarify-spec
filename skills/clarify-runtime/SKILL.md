# clarify-runtime：Agent 间指令与运行时消息的消歧规范

本 Skill 解决一个问题：Agent 向 Agent 传递的指令与消息产生二义性，而接收方没有回溯信道可以追问。涉及两类输入。**自然语言派发指令**：主 Agent 向 sub agent、任务编排层下发的任务文本。**结构化运行时消息**：A2A 消息体、工具调用的参数与返回、进度事件、错误事件、心跳。人向 Agent 下达的指令不属于本 Skill，由 clarify-spec 承担。

C 类读者是纯机器或另一个 Agent，执行最严格的纪律：信封契约、意图枚举、机器可读错误、情态字段化、时间绝对化。

## 规范对象

**自然语言派发指令**（delegation instructions）：主 Agent 派发的任务说明、编排层生成的步骤文本。适用人类表达规则（H-A1…H-A14, R-A1），核心失效模式：强度漂移、模糊量词、一句多义、悬空指代。

**C. 运行时消息**（runtime messages）：A2A 消息体、工具调用与返回、进度事件、错误事件、心跳。
核心失效模式：无信封与关联（C-1）、意图自由文本（C-2）、错误只写在自然语言里（C-6）、相对时间（C-10）、推测词未字段化（C-5）。

规则全文：
- `references/human-expression-rules.md` — 派发指令适用的表达规则条目。
- `references/runtime-message-rules.md` — C 类全部规则条目（C-1…C-12）。
- `references/protocol-mapping.md` — C 类字段与 A2A / MCP 的逐字段对齐映射（含 `--profile` 可执行模式）。

## 使用时机（两个姿态）

**姿态一·接收侧旁路校验**（inbound validation）：接收方在采纳一条派发来的指令或消息之前，对其做旁路校验。发现违规时的行为契约：输出违规清单与建议澄清问题发回发送方；无法追问时，声明将采用的解释并继续。**绝不静默改写收到的指令**——收到的指令是发送方的事实，静默改写即篡改。输入已合规时直接说明。

**姿态二·发起侧构造**（outbound construction）：派发任务或发出消息之前先跑确定性 linter 自检。再按契约构造或修复输出，使接收方无需追问。

用户未指定姿态时按角色推断（「校验/检查收到的」→ 接收侧；「构造/生成/修复这条消息」→ 发起侧），并在一行内声明推断结果。

## 流程

1. **分类**。判定输入是自然语言派发指令还是结构化消息；结构化消息进一步判定消息类型（委托/响应/错误/工具返回）。混合输入分段处理。
2. **选姿态**。接收侧校验或发起侧构造；推断时一行声明。
3. **机械扫描**。先跑确定性 linter 得到硬性违规清单：自然语言指令用 `scripts/spec-lint.py`；JSON 消息用 `scripts/msg-lint.py`（对接 A2A / MCP 时加 `--profile a2a|mcp-request|mcp-result`，字段映射见 `references/protocol-mapping.md`）。
4. **处理**。接收侧：整理违规清单与建议澄清问题，或声明将采用的解释。发起侧：逐条修复违规，同时满足以下红线：
   - 保留原文全部事实、条件、范围限定与量化指标。更短的措辞若损失必要精度，保留较长措辞并在输出中标注。
   - 保留每个情态表达的强度；禁止把 hedges 升级为事实，禁止添加原文没有陈述的原因、频率或机制。
   - 不改动消息信封字段名（linter 按字段名匹配）。
5. **专项补齐**（仅发起侧）。补齐信封六字段；错误对象补齐四字段；推测落实为 confidence 字段；相对时间落实为绝对 UTC 时间戳。消息中的自然语言字段（message、detail、reason）按 Strict 模式执行表达规则。
6. **输出**。见输出契约。

第 3 步中需要语义判断的违规（H-A1、H-A4、C-3、C-4 等）由你在通读中标记，linter 只负责机械规则。

## 输出契约

**接收侧校验姿态**：输出违规清单、建议澄清问题与（无法追问时）将采用的解释：

```markdown
| 违反规则 | 原文 | 建议澄清问题 |
|---|---|---|
| H-A7 模糊量词 | 处理各种异常格式。 | 「各种」指哪些格式？请枚举。 |
| C-10 时间绝对化 | "try again later" | 重试的绝对时间是什么？ |
```

无法追问时，表后加一行：`将采用的解释：<对每处歧义选定的解读>`。输入已合规时直接说明，不输出空表。

**发起侧构造姿态：只输出构造/修复后的指令文本或消息体。** 不加前言、不附违规计数、不做变更总结。调用方需要能直接把结果粘贴进派发 prompt 或消息队列。唯一的允许附加项：因保精度而有意保留的较长措辞，输出末尾加一行 `保留原表述：<短语> — <损失的精度>`。无此类项时省略该行。

**应请求输出规则表**。用户要求「show the diff」「改了哪些」「哪些规则」时，输出对照表：

```markdown
| 违反规则 | 原文 | 改写后 |
|---|---|---|
| C-10 时间绝对化 | "try again later" | "retry_at": "2026-10-02T08:05:00Z" |
```

表后加一行说明有意未简化的内容及其原因。

## 边界

**会做**：
- 接收侧旁路校验派发来的自然语言指令与结构化消息，输出违规清单与建议澄清问题。
- 发起侧构造符合信封契约、意图枚举与机器可读错误的指令与消息。
- 构造姿态默认只返回结果本身；应请求时点名所用规则。
- 保留原文全部事实、条件、范围限定、量化指标与情态强度。

**不做**：
- 不静默改写收到的指令或消息。校验姿态只报告、建议澄清或声明解释。
- 不处理人向 Agent 下达的指令与人审阅的过程文件（需求、PLAN、ADR、CHANGELOG）——属于 clarify-spec。
- 不验证会话历史中 correlation_id 的真实性或实体标识符的可解析性——这需要运行时上下文，留给集成测试。
- 不把 linter 的零违规当作合格证明。linter 是下限检查，语义规则仍需模型执行。
- 不为简洁而损失精度。压缩不是目标，消歧才是；当句子已无非确定解读时停止。
