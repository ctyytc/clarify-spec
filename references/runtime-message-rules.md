# Agent 运行时消息规范 / Runtime Message Rules

本文件定义规范对象 C：运行时在 Agent 之间、Agent 与工具之间传递的消息体。与 A（人类表达）、B（文档类过程文件）并列。

为什么 C 类需要独立规则：运行时消息的读者是纯机器或另一个 Agent，无人工兜底、不可追问、对话上下文易失。B 类过程文件至少假设会有人归档审阅；C 类连这个假设都没有。因此 C 类执行全部规则中最严格的纪律。

适用文本：A2A 消息体、工具调用的参数与返回、进度事件、错误事件、心跳。

与 A/B 类的关系：C 类的自然语言字段仍受 A 类全部表达规则约束，包括 message、detail、reason。C 类额外规定信封、意图、错误与交付语义。机械检查由 `scripts/msg-lint.py` 执行。

## 1. 信封契约（C-1，硬性）

每条消息必备六字段：

- `message_id`：全局唯一，建议 uuid4。
- `sender` / `recipient`：Agent 规范名，取自注册表，不即兴命名。
- `timestamp`：UTC ISO 8601（RFC 3339，带 Z 或显式时区偏移）。
- `correlation_id`：因果链标识。响应必须继承所响应消息的 correlation_id，否则无法归因。
- `intent`：见 C-2。

依据：W3C Trace Context 的关联语义；RFC 5424 的 syslog 信封结构。

## 2. 意图枚举（C-2，硬性）

`intent` 取值仅限封闭枚举：`delegate`（委托）、`query`（查询）、`respond`（响应）、`report`（报告）、`clarify`（请求澄清）、`cancel`（取消）。禁止自由文本意图——意图是路由依据，不是语气。

依据：言语行为理论（Austin / Searle）：每个 utterance 本身是一种行为；A2A 协议的任务消息分类实践。

## 3. 一消息一意图（C-3，硬性）

一条消息只承载一个意图。确需批量操作时设 `batch: true`，且每项可独立成败，返回逐项报告失败项。单消息多意图会让部分失败无法归因。

依据：HTTP 逐请求语义；消息队列的逐条确认模式。

## 4. 实体锚定（C-4，硬性）

引用实体必须使用不可变标识符：任务 id、文件路径加行号、commit hash、URI。禁止仅用名称、「上述」「刚才那个」——对话上下文是易失的，同一名称在不同时刻指向不同实体。

依据：STE 指称一致原则的运行时版；RFC 3986 的 URI 语义。

## 5. 情态字段化（C-5，硬性，继承 R-A1）

置信度与假设是数据，不是修辞。消息必须显式携带 `confidence`（0.0–1.0，或枚举 confirmed / inferred / assumed）。自然语言字段中出现推测词（`可能`、`也许`、`maybe`、`perhaps`）而消息无 confidence 字段，即违规——推测必须可机读，否则下游 Agent 只能猜。

依据：A 类 R-A1（情态即内容）的运行时延伸；RFC 2119 情态语义的数据化。

## 6. 错误机器可读（C-6，硬性）

error 对象必备四字段：

- `error_code`：稳定枚举，禁止随文案漂移（同一错误的 code 不变）。
- `message`：人读一句话，受 A 类规则约束。
- `retryable`：布尔。下游据此决定重试还是升级。
- `recovery_hint`：建议动作，命令式句。

禁止只把错误写在自然语言里。依据：RFC 7807 problem+json；ISO/IEC 25010 可维护性。

## 7. 交付语义（C-7，建议）

声明 `ack_required` ∈ {none, ack, response} 与 `timeout_seconds`。需要重试的写操作必须携带 `idempotency_key`，使重试安全。

依据：RFC 9110 的幂等性与安全方法语义；MQTT QoS 分级思想。

## 8. 工具调用契约（C-8，建议）

每个参数声明：类型、单位、取值域、默认值、失败模式。返回结构必须显式表达部分失败（`partial: true/false`），禁止整体静默成功。

依据：OpenAPI / JSON Schema 参数语义；可观测性工程实践。

## 9. 上下文自足（C-9，硬性）

消息不得依赖「对方记得」。所需上下文要么内联自带，要么显式引用可检索 artifact（文件路径加版本或 commit hash）。无状态不是省略上下文的理由，而是把上下文的引用显式化。

依据：REST 无状态原则；十二要素应用的显式契约。

## 10. 时间绝对化（C-10，硬性）

禁止相对时间：`稍后`、`一会儿`、`马上`、`尽快`、`5 分钟后`；`later`、`in a while`、`ASAP`、`soon`、`shortly`。一律使用绝对 UTC 时间戳。相对时间的参考系（谁的「现在」）在异步系统中不确定，这正是二义性的来源。

依据：RFC 3339；分布式系统不共享时钟的通行假设。

## 11. 大负载外置（C-11，建议）

payload 超过 2000 字符必须放入 artifact 存储，消息体只传 `artifact_ref`。大负载消息挤占双方上下文窗口并降低路由效率。

依据：消息层只传引用是消息队列与事件系统的通行做法；性能维度的 token 预算纪律。

## 12. 版本协商（C-12，建议）

消息携带 `schema_version`（SemVer）。破坏性变更升主版本。旧主版本至少在两个发布周期内保持可解析。

依据：SemVer；OpenAPI 版本化实践。

**msg-lint 的设计边界**：它只解析 JSON 消息并检查字段级契约。它不验证 correlation_id 是否真实存在于会话历史。它也不验证实体标识符是否可解析。这些检查需要运行时上下文，留给 Agent 与集成测试。与 spec-lint 相同的哲学：linter 是下限检查，不是充分条件。
